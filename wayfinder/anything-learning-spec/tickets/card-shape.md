# What goes on a card

## Question

Cards are one flat shape across all subjects. Lock the exact card shape: which fields are core and always present, which are optional, how the general attachment slot works (what it holds, how a card declares that it needs one), and how a pack adds its own extras without the core learning what a subject is.

Concrete scenarios to stress: a Polish word needing audio and an example sentence; an anatomy term needing a labelled diagram; a music interval needing a played sample; a code snippet needing a syntax-highlighted monospace face. All four must fit without the core knowing what Polish, anatomy, music, or code are.

## Resolution

Cards are two-sided: a prompt side and an answer side. A one-sided card is a card with an empty side; no separate card type.

Each side is an ordered list of parts. The common part is text. Any part may be an attachment (audio, image, or anything else a pack defines). The core lays parts out in order and does not know what any part means.

Subject knowledge lives on the pack, not on the card. The core never learns what Polish, anatomy, music, or code are. A card carries plain tags for finer detail (grammar, difficulty, topic) that the pack understands but the core treats as opaque strings.

A card records its origin - written by the learner, generated by the provider, or imported - as a note only. Origin never changes card behaviour, so an edited generated card is simply the learner`s.

Every card carries a plain-text summary, built by the pack. This is what any checker reads, so one checker can assess a Polish card and an anatomy card without knowing either subject, and a checker can be swapped without touching a single card.

Importing cards is all-or-nothing. A malformed card rejects the whole batch with an error naming what is wrong and where. Rationale: a silently dropped card is a hole in the learner`s progress record that cannot be seen. The cost is accepted deliberately - the good cards in a bad batch are also rejected.

Cards are imported in chunks, not one giant paste. An AI asked for 200 cards degrades near the end; each chunk must be correct and is added as a batch, all-or-nothing.

Deck relevance is two separate checks. A broken card (missing field, front equals back) is caught by hard rules, instantly, always, at no cost. An out-of-place card (well-formed but belongs elsewhere) is a judgement, not a rule, so it is asked of a pluggable checker and the card arrives flagged for the learner to accept or reject - never blocked. If no checker is available or the provider is unreachable, the batch still lands unflagged.

The checker is pluggable, on the same seam as packs. Laya (Apache-2.0, CPU-capable, 100+ languages, ~33ms per decision, no text generation so it cannot hallucinate) is a viable local free checker. It requires fine-tuning on learner card data to be sharp on this narrow task; out of the box it is general-purpose and unreliable here. The seam does not assume Laya.

## Answers given during the session

1. Is a card one thing or two? -> Two sides; one-sided is an empty side.
2. Is a side always just text? -> A side is an ordered list of parts; any part may be an attachment.
3. Where does subject knowledge live? -> On the pack. Cards carry plain tags only.
4. Does origin change behaviour? -> No. Origin is recorded as a note.
5. What happens on a malformed paste? -> Reject the whole batch with a detailed error.
6. Chunked or one giant paste? -> Chunked, each batch all-or-nothing.
7. How is a card that does not belong detected? -> Hard rules for broken cards; a pluggable checker flags out-of-place cards; the learner decides; never blocked.
8. Does a card carry something a checker can read? -> Yes. A pack-built plain-text summary.
