Subscription recovery - Grill Notes

Status: Locked
Date: 2026-10-28
Source: this session's request (quoted below), sibling pack
docs/features/system-provider-subscription/, map line "A paid system provider"

What this feature is about

- A learner who bought the subscription on one browser can get a working pass on
  another browser (or after clearing site data) by proving they control the
  email they paid with.
- Stripe stays the record of who is subscribed. The service gains no database,
  no account, no password and no stored email.
- The new browser ends up holding its own signed pass, exactly like one issued
  after a finished checkout; the old browser's pass keeps working until it
  expires.
- It does NOT add a login, a profile, settings or card sync, SMS, or recovery
  for the learner's own (bring-your-own) provider.
- It does NOT recover a cancelled or unpaid plan; the learner sees that the
  subscription is not active and is offered the existing Subscribe button.

   (Dictated; "because we don't have a." is a false start. Kept verbatim.)

Answer:
- The pass stays browser-local, but a learner can ask for a new one on any
  browser by typing the email they paid with.
- The service recognises a subscriber through Stripe, not through a record of
  its own: it looks up the Stripe customer for that email and the live
  subscription behind it.
- Nothing new is stored: no ID to keep, no profile, no password.

Why:
- The complaint is real and the current behaviour is the worst kind of loss:
  clearing site data silently destroys something paid for
  (v1/src/lib/browser/repository.ts:368 `system-license`).
- A saved ID only works if the learner still has it — which is exactly what
  losing the browser takes away.
- An account with name, email and password would store personal data and add a
  password surface the app has never had.
- Stripe already holds the email and the subscription, so it is the cheapest
  honest record. This rules out a new database, device sync and a login.


2. "perfect!!! lets use stripe!!!"

Answer:
- Stripe is the record of who subscribes: the customer, the email on it, and the
  live subscription state.
- The service derives everything from Stripe per request; it keeps no copy.

Why:
- Checkout already runs in subscription mode and creates a Customer, so the
  email exists at Stripe
  (v1/server/src/stripe.ts:181 `createCheckoutSession`, mode: "subscription").
- The service is stateless by design today; a recovery flow that asks Stripe
  each time preserves that property
  (v1/server/src/subscriptions.ts, `StatusCache`).
- Rules out: an accounts table, a saved recovery ID, a separate identity
  provider.


3. "can we use clerk?"

Answer:
- Not in this pack.
- If real accounts (settings or card sync, not just recovery) are wanted later,
  Clerk is a fair candidate then. This design does not block it: the app only
  ever consumes a pass.

Why:
- Clerk is a hosted login: a third-party script in the app, a Clerk secret on
  the service, session tokens to verify, and somewhere to map a Clerk user to a
  Stripe customer — the one thing this service has deliberately never held.
- It replaces "Local only. No account." on every screen for every learner, which
  is a product change larger than this recovery pack.
- Cost is not the objection (free to 10k monthly users). The recovery work — mint
  a pass, check the subscription live — remains either way, so Clerk would add a
  platform on top of it, not instead of it.
- Source: learner question in this session; product promise as written in the
  app's sidebar and the system-provider ticket.


4. "Which identity route should this recovery pack take?"

Answer:
- Email one-time link: the learner types the email used at Stripe Checkout, the
  service emails a short-lived link, and opening it in the new browser stores a
  fresh pass.
- No password, no account; the service stores nothing.

Why:
- Uses the email Stripe already has; nothing to remember except an inbox the
  learner already owns.
- Out: a saved recovery code (lost with the old browser, so it fails on the exact
  day it is needed) and an email + password account (stored personal data,
  password reset, breach surface).
- Recorded after the three options were put with these trade-offs; the learner
  first asked about Clerk (entry 3) and then chose this route.


5. "How long should a recovery link live, and which spam limits do we apply?"

Answer:
- The link lives 30 minutes and can be opened more than once inside that window;
  redeeming always re-checks the live subscription with Stripe.
- Each address may request 5 links an hour.
- Each email address gets at most one link every 10 minutes, tracked as a hash in
  memory only.

Why:
- Mail can be slow; 30 minutes leaves room without leaving a leaked link useful
  for long.
- Limits stop the form becoming a way to flood a stranger's inbox; the in-memory
  map fits the service and clears on restart, exactly like the rate limiter
  (v1/server/src/http.ts:28).
- Not single-use, because single-use needs stored state, and the live Stripe
  check already limits what a reused link achieves.


6. "What should the form answer when the email has no live subscription?"

Answer:
- Always the same sentence and status: "If that email has a subscription, a link
  is on its way."
- A sending failure is logged without the address, and the answer is unchanged.

Why:
- Any difference in wording or status would let a stranger test whether a given
  address is a customer.
- Cost accepted: a subscriber who mistypes their email gets silence; the card
  says "Use the email you paid with" and the form stays usable.


Decisions taken under delegated authority (not asked)

- Mailer: Brevo free tier, sent over the HTTPS API
  (POST https://api.brevo.com/v3/smtp/email), no SDK, no SMTP client.
  Source: the learner asked for "a free mailer for now" and delegated the
  choice on 2026-10-28 (.reports/goal-provider-relay-merge.md). Brevo verifies a
  single sender address by email, so no domain is needed; Resend would need a
  verified domain before mailing arbitrary learners.
- Recovery is optional and off by default: it is available only when
  BREVO_API_KEY, RECOVERY_SECRET and RECOVERY_FROM_EMAIL are all set. Otherwise
  /api/config reports recovery: false, the form is not rendered, and the endpoint
  answers 503. Existing deployments keep working untouched.
- A separate RECOVERY_SECRET signs links, not LICENSE_SECRET, so rotating one
  does not invalidate the other.
- Link token shape: base64url JSON {v, email, iat} plus an HMAC-SHA256
  signature, 30-minute expiry (RECOVERY_TOKEN_TTL_SECONDS, default 1800).
- One email may cover more than one live subscription: the most recently
  renewing live one is used. (Inferred; Stripe allows several subscriptions per
  customer.)
- Stripe filters customers by email exactly as stored, so the service asks for
  the address as typed and again in lowercase, and uses both answers
  (v1/server/src/stripe.ts:246). A single exact query would silently miss a
  learner who typed different case at Checkout.
- Redeeming stores the pass and switches the provider to the system lane, the
  same end state as a finished checkout.
- The email carries one sentence, the link and the expiry; no learner text, no
  card data, no price.
- Brevo processes the address to deliver the message; the service itself neither
  logs nor stores it.
- The pass format does not change; a recovered pass is indistinguishable from one
  issued at checkout.

Non-goals

- No account, password, session or profile on the service.
- No sync of settings, cards, progress or the provider key between browsers.
- No recovery of a cancelled or unpaid subscription; the existing Subscribe
  button is the path back.
- No SMS or other second channel.
- No recovery for the bring-your-own provider lane.
- No change to backup rules: the pass still never enters a backup.
- No marketing or notification email; recovery links only.

Edge cases named

- Email mistyped: silence by design; the card repeats "Use the email you paid
  with".
- Mail delayed past 30 minutes: the link says it expired and the form offers a
  new one (subject to the 10-minute per-email cooldown).
- Link opened twice: both openings work inside the window, each stores a pass.
- Link opened on the same browser that already holds a pass: replaces it, no
  harm.
- Subscription cancelled after the link was sent: redemption refuses with "This
  subscription is not active."
- Service restarted between request and redeem: the link still works, because
  nothing about it lived in memory.
- Mailer down: the learner sees the same sentence and tries again; the operator
  sees one server-side log line without the address.
- The learner's browser blocks the service: the form reports the plain
  "could not reach" sentence, as the subscription card already does.

7. "Should the recovery form always be visible on the Provider tab?"
   (Asked while reviewing the pre-impl simulation.)

Answer:
- Yes: the section sits under the System card in both states, also when this
  browser already holds a working pass.

Why:
- A learner with a working laptop may still want their phone; hiding the form on
  an active card leaves no visible road.
- It stays quiet and secondary, so it does not compete with Subscribe or with
  the provider switch.


8. "OK, we can leave the email link. Since the user actually has to. The phone.
   Ah, the unit. So, yeah. And I don't know if there's a way we can validate that
   email. Is connected to another account, so it can be one email. For one.
   Flask card accounts. Is that possible? Speak to me."
   (Dictated; "Flask card" is "flashcard". Kept verbatim.)

Answer:
- No, not without keeping a record, and this pack keeps none.
- Stripe can say that some customer holds that address. It cannot say that the
  person typing it is that customer; only the inbox proves that.
- One address may carry more than one live subscription; recovery uses the live
  one that renews latest (see "Decisions taken under delegated authority").

Why:
- One email for one account needs stored state — an accounts table or a device
  id — which is the thing this service has refused since the system-provider
  pack.
- Binding a pass to a device would break the laptop-and-phone case that makes
  recovery worth building.
- A shared inbox really can hold two subscriptions. Refusing the second does not
  stop the sharing; it only locks out the person who paid. Whoever can read the
  inbox is the owner, by design.

  entry 6 forbids.
- Entry 4 had already locked the link. This entry records the alternative as
  considered and rejected so it is not reopened without new facts.

Amendment 2026-10-29 - the link works once

10. "make the link single use, fix the cold start timeout so the first email
   doesnt fail."
   (Asked after the pack shipped; kept verbatim.)

Answer:
- A link buys one pass. Redeeming writes the token's issue moment to the Stripe
  customer's metadata (recovery_used_iat); any link issued at or before that
  moment is refused with "That link has already been used. Ask for a new one."
- A link requested after a redemption still works.
- The service still stores nothing of its own: the mark sits on the Stripe
  customer, the record that already holds the address and the plan.
- The browser now waits 60 seconds for a service answer instead of 20, because
  the free plan sleeps when idle and its cold start can take most of a minute.

Why:
- Supersedes entry 5 ("Not single-use, because single-use needs stored state")
  and its edge case "Link opened twice: both openings work inside the window".
  The learner asked for one use after the trade-off was put to them: a forwarded
  or archived link should not be a second key.
- The stored state entry 5 worried about is not a database. The customer record
  is its natural home: the mark survives a restart and a redeploy, which an
  in-memory set would not, and the free plan sleeps whenever it is idle.
- One-second resolution is enough because the per-email cooldown is ten minutes:
  two links for one address can never share an issue second.
- Cost accepted: opening the link on the wrong browser spends it, and the learner
  asks for a new one. The form says so before they click.
- The mark is written before the pass is minted. If Stripe refuses the write, no
  pass is handed out, so a success can never be replayed.
- A simultaneous double open is not a compare-and-set and can both succeed; any
  later use is refused. Accepted: both openings would come from one page load.
