What this feature is about

- Every pack, every deck and every card gains its own detail page. The
  learner calls it a "Dictionary": detailed knowledge about the thing
  being learned, not a word definition.
- A page carries text, images and/or video: a short story, the origin of
  the idea, a short description that makes it memorable.
- The pages connect upward: card page, then deck page, then pack page.
- Course material can be written after the cards are generated. Writing
  course material and generating cards are separate jobs.
- The pages serve two routes: lessons in course order, and reference
  opened on demand.
- Authoring becomes its own feature with shared tools: a Course Builder
  workspace plus Edit buttons on each page. Both manual writing and
  optional AI drafting are supported; a draft is reviewed before saving.
- The same tools serve personal courses and the shipped built-in
  courses.
- A learner may personalise a built-in course privately; only the course
  author changes the shipped course.

- A save that would pass the cap is refused with a plain reason: link the
  video instead, or remove a kept file. The editor shows a meter of kept
  megabytes against 300 MB.
- Linked media does not count towards it: nothing is copied onto the
  device.
- What 300 MB costs: a full backup loads every kept blob and builds the
  zip in one blocking step, so it needs about twice the total in working
  memory, about 600 MB when the library is full. On a phone that can end
  in a crashed tab. The mitigations belong to the open export question:
  warn with the size before a backup, write the zip in pieces, or advise a
  phone to export one pack at a time.

Why:
- The learner answered "300" after being shown 20 / 150 / 250 with the
  backup arithmetic. 150 MB was the recommendation; the learner chose
  more room and accepted the larger backup peak.
- Source: user message 2026-10-29 ("300").

27. "refuse local video for phone unless its from internet"

Answer:
- On a phone, a video part cannot be kept in the browser. The authoring
  screen offers only the address field for a video, and choosing a video
  file is refused with a plain reason: on a phone, videos are linked, not
  kept.
- Pictures may still be kept on a phone. The rule names video only.
- "From the internet" means a link: YouTube, a Drive preview or any web
  address. A video file that was downloaded is still a file, and is
  refused.
- The rule covers adding a video on a phone. A kept video that arrives
  inside an imported or shared pack still plays; this is a rule on
  authoring, not a lock on the page.
- A phone is read as a mobile browser. A tablet that reports itself as a
  desktop is not caught by the rule; the size caps still apply there.
  **Revised by entry 28: the rule follows the cause, so tablets are
  included.**

Why:
- The learner's call: a phone should not carry kept video. It removes the
  heaviest case from the phone's store and from its backup, which needs
  about twice the kept total in working memory.
- Cost, named: a phone author cannot add footage they shot unless it is
  posted somewhere first.
- Source: user message 2026-10-29 ("refuse local video for phone unless
  its from internet").

28. "follow the cause, tablets too"

Answer:
- The rule follows the cause, not the device name: on any touch-first
  mobile browser, phone or tablet, a video part must be linked, never
  kept. Pictures may still be kept.
- Read as: a touch device running a mobile system (Android, iOS, iPadOS),
  including an iPad that reports a Macintosh user agent. A touch-screen
  laptop running Windows, macOS or ChromeOS counts as a computer and may
  keep video.
- The rest of entry 27 stands: a downloaded file is still a file, the rule
  covers authoring only, and a kept video inside an imported or shared
  pack still plays.

Why:
- The risk is the same on a tablet: a full 300 MB backup peaks near 600 MB
  in working memory, iPad Safari gives a tab about a gigabyte, and iPads
  are evicted and shipped small like phones.
- A phone-only rule would miss every iPad, because iPadOS presents a
  desktop user agent.
- Source: user message 2026-10-29 ("follow the cause, tablets too").

29. [agent decision] Do the pages travel with an exported pack and with
    the full backup?

Answer:
- Yes to both, with one difference. A shared pack (JSON or zip) carries
  the pack page, its deck pages and its card pages, and the kept media
  those pages point at travels as files the same way card media already
  does. The full backup carries the pages and the learner's reading
  traces. A shared pack never carries reading traces.
- At the 300 MB cap a full backup still peaks near 600 MB of working
  memory (entry 26). Before a backup starts, the app states the size it
  is about to build; on a touch-first device it also suggests exporting
  one pack at a time.
- A streaming zip was considered and not built. The backup is assembled
  in one blocking step today (zipSync), and restore already promises
  all-or-nothing; putting that promise at risk to remove a warning is a
  bad trade for this pack.

Why:
- Pages are course material, so they belong to the course and leave with
  it. Traces are one learner's record (entry 21), like evidence, so they
  belong to the learner's own backup and nowhere else.
- Media already travels by the ids named inside the exported JSON
  (archive.ts), so pages join one reference set instead of inventing a
  second packing rule.

Source: entries 21 and 26; open question 1; code archive.ts:114,
bundle.ts:806.

30. [agent decision] How is a personal change to a built-in course
    stored so it stays private: a personal copy of the pack, or an
    overlay on the shipped content?

Answer:
- An overlay, never a personal copy of the pack. Each page is one record
  keyed by the pack, deck or card it belongs to and stored in the
  learner's browser.
- A shipped page is written only when the learner has not edited that
  page. A seed leaves an edited page alone, and deleting the learner's
  overlay brings the shipped page back on the next seed.

Why:
- A whole-pack copy forks the course and goes stale as soon as the
  shipped cards update. An overlay keeps one shipped course and one
  private layer above it, which is exactly entry 6's promise.
- The app already remembers a deleted built-in card without touching the
  shipped pack (seed.ts), so the overlay follows a rule that exists.

Source: entry 6; seed.ts.

31. [agent decision] Draft with AI: which provider lane, what does the
    prompt see, and what does it cost?

Answer:
- The existing provider lane: the learner's own key, or the paid system
  provider. No new service is added.
- One draft is one provider call. The exact prompt is shown and approved
  before it is sent, the same prepare-and-approve path generation uses,
  and the answer lands in the editor as unsaved text. Nothing is saved
  until the learner presses Save.
- The prompt sees the page's level, the pack, deck and card it belongs
  to (names, the card's summary, question and answer text), the pack's
  language pair and the learner's own instruction. It never sees
  evidence, settings, a provider key or a backup.
- Cost: one call. On the custom lane it is one call to the learner's own
  provider; on the system lane it is one call through the same relay
  that answers a hint or a summary.

Why:
- Entry 4 already says drafting is optional and reviewed before saving;
  this fixes the lane without pricing a new vendor.
- The disclosure matches the provider screen's existing promise: card
  text may be sent, evidence and settings never are.

Source: entries 2 and 4; provider.ts:59; prepare.ts.

32. [agent decision] Does editing a page change card identity?

Answer:
- No. A page is a separate record keyed by the pack, deck or card it
  belongs to. Saving a page writes only that record: no card is created,
  retired or edited, and every evidence row stays with its card.

Why:
- Card identity changes when the question or answer changes (entry 4).
  A page is neither, so it follows the teaching-material rule: edited in
  place, never a new card (GRILL-teaching-layers entry 27).
